# Изменяемые политики Learning

Эта страница отвечает на вопрос «какую настройку менять?» по **владельцу и
области действия**. Значения по умолчанию сохраняют уже принятое поведение.
Проверка границ происходит при старте backend или при создании bounded client
policy. Изменение policy влияет только на новые операции; опубликованные
ревизии и сохранённые evidence не переписываются. Media transport (#235),
processor (#236), playback (#239) и offline manifest (#242) имеют отдельные
namespaces.

| `learning.study.retention.snapshot-horizon` | Через сколько после старта сессии удаляется её снимок: презентации и всё, что на них висит (`study_exposure`, раскрытия подсказок и транскрипта, pair-проверки, строка AI-оценки), презентации в результате `study.start` (receipt сжимается до заглушки), затем генерации кандидатов, которые никто не читает. Владельцы и приватный API не затронуты | Boolean; `false` |
| `learning.community.public-routes.guest-per-minute` / `coarse-per-minute` / `overflow-per-minute` / `account-per-minute` | Публичное чтение: лимиты запросов в минуту на инстанс (окна по монотонным часам). Гость — по сети клиента (IPv4-адрес, IPv6 `/64` через `learning.trusted-proxy-cidrs`); для IPv6 дополнительно все гости одного `/48` вместе (запрос должен пройти оба предела, ротация `/64` внутри сайта ограничена); гости, не нашедшие места в таблице гостей, делят один общий overflow-бакет; вошедший — по аккаунту в **отдельной** таблице (гости его не вытесняют). Каждый запрос считается, найден он или нет; отказ ничего не списывает. Вошедший учитывается фильтром публичной цепочки до запроса к Identity (один токен не может породить неограниченное число `/userinfo`), гость — сервисом. Превышение — 429 `RATE_LIMITED`, `Retry-After` — реальный остаток окна. Лимитер в памяти инстанса (при N инстансах предел ×N): чтение не должно превращаться в запись в БД | Count в минуту; `120` / `600` / `600` / `600`; 1–100000 (`coarse`, `overflow` — до 1000000) |
| `learning.community.public-routes.max-tracked` | Публичное чтение: размер каждой из таблиц лимитера (гости, `/48`, аккаунты). | `learning.community.public-routes.max-concurrent` | Публичное чтение: bulkhead — сколько публичных чтений инстанс обслуживает одновременно (общий для чтения колод и публичных медиа, Share/9; все шаги, включая запись кэша заголовков, держат разрешение). Гости могут занять не больше `max-concurrent - 1` мест — одно всегда свободно для вошедшего. Семафоры берутся `tryAcquire` до транзакции и соединения; лишнее чтение отвечает сразу `503 PUBLIC_READ_BUSY` с `Retry-After: 1` и не встаёт в очередь пула. Это ограничивает, но не исключает конкуренцию с приватным API за общий пул: при старте (маршруты включены) сумма `max-concurrent` + `learning.jobs.max-concurrency` (роли `worker`/`all`, задачи включены) должна оставлять не меньше 3 соединений эффективного `spring.datasource.hikari.maximum-pool-size`, иначе запуск падает с понятным сообщением. **Запаса нет:** при умолчаниях (пул 10, `max-concurrent` 3, задачи 4) остаётся ровно 3 — повышать `max-concurrent` можно только вместе с `maximum-pool-size` | Count; `3`; 2–64 |

| `MNEMA_OG_META_UPSTREAM` / `MNEMA_OG_META_RESOLVER` | Автономный образ frontend: `host:port` Learning для `GET /api/public/meta/decks/{code}/head` (генератор `40-gen-app-config.sh` пишет `conf.d/mnema-og-meta.inc`) и, если это имя, IPv4 resolver. | `learning.community.profile-lookups.instance-per-window` / `complaints-per-window` / `owner-per-window` / `reporter-per-window` | Один общий бюджет всех вызовов Learning к публичному поиску логина Identity (`GET /api/accounts/profiles/by-username/{u}`; `platform.security.ProfileLookupBudget`; выдача доступа по логину, Share/13, #435, и жалобы на профиль, Share/15, #437). Identity ограничивает этот поиск **по сети**: 60 запросов за **фиксированное окно в 15 минут** (`RateLimits`), и все вызовы Learning идут с одного адреса, поэтому бюджет общий для всех владельцев и инстансов. Learning считает в той же единице: фиксированное окно **15 минут** по монотонным часам, в памяти инстанса (окно начинается с первого допущенного вызова, а не выровнено с окном Identity). Пределы: `instance-per-window` — всего на инстанс (оба пула вместе); `complaints-per-window` — из них не больше столько на жалобы, поэтому жалобы не могут вытеснить выдачу доступа (остаётся не меньше 30 из 40); `owner-per-window` — на владельца (выдача доступа); `reporter-per-window` — на жалобщика. Отказ — 429 `RATE_LIMITED`, `Retry-After` — реальный остаток окна (в фиксированном окне раньше место не освобождается), **до** обращения к Identity. Если `429` отвечает сам Identity (его ответ не несёт `Retry-After`), весь бюджет считается исчерпанным до конца текущего окна и вызывающий получает тот же остаток, а не выдуманные 30 с. Порядок прежний: допуск аккаунта, проверка открытой жалобы (повтор не стоит поиска), бюджет, Identity. S3 endpoint, region, bucket и credentials находятся в том же namespace
`learning.media.upload`, но относятся к подключению, а не к пользовательским
лимитам. `allow-loopback-http` разрешает HTTP только для локального MinIO.
`GET /api/media-assets/upload-policy` возвращает авторизованному browser
актуальные per-kind byte caps для проверки перед резервированием asset;
`MediaUploadSettings.validate` остаётся обязательной серверной проверкой.
Медиа transport принимает файл как входные байты: фактический codec и
длительность проверяет processor. Изменение `max-video-bytes` не меняет
допустимые пять минут; это отдельная настройка обработки. Processor включается
отдельным `learning.media.processing.enabled` (default `false`), после настройки
локальных Docker image/binary и work-root. Эти параметры задают способ запуска,
а не продуктовый лимит. Browser media polling: очередь upload 2 одновременных
transfer, 2–15 s backoff; reader 2–15 s для pending и renewal до истечения URL;
список колод — 45 s на видимой вкладке. Все три клиента имеют разные owners.
Manifest и GC contracts описаны в
[`media-offline-manifest.md`](media-offline-manifest.md) и
[`media-gc.md`](media-gc.md). GC scan interval задаётся отдельно
`learning.media.gc.scan-interval` (`PT10M`) и влияет только на частоту scheduler.

`max-active-per-account` draft допускает рост до 1000. Web list aggregation
запрашивает страницы по 20 и обнаруживает превышение 50 страниц,
вместо успешного ответа с неполным списком. При изменении верхней
границы draft count нужно одновременно обновить этот клиентский контракт.

## Не runtime policy

`NativeDocumentReader` и Angular renderer limits (1 MiB, 10 000 nodes,
depth 32, scalar 32 KiB), storage object layout, counted-page dimensions,
exercise response bounds и pagination maximum являются версионированными
wire/storage invariants. Их меняют вместе с контрактом, fixtures и обеими
сторонами API. `BaselineReducer` interval ladder принадлежит versioned learning
algorithm; изменение требует нового policy version/hash и migration evidence.
Лимиты хаба колоды (#285) — те же версионированные wire-инварианты, а не Spring-ключи: не более 10
«Эталонов» на колоду, bulk-удаление до 500 материалов за запрос порциями по 100 (одна атомарная публикация на порцию),
семь дней в `dueByDay`. Они зафиксированы в [`contracts/decks/hub.json`](../../contracts/decks/hub.json), а
`EXEMPLAR_LIMIT_REACHED` и `BULK_SELECTION_TOO_LARGE` возвращают значение в поле `limit`.
Лимиты доступа «По приглашению» (Share/13, #435) — тоже контрактные константы, а не Spring-ключи: не более 20 активных и 200
сохранённых приглашений на колоду; 20 открытых запросов и 5 новых запросов за скользящие 24 часа на запрашивающего; повторный
запрос после отклонения через 30 дней; одно уведомление автору на колоду за календарный день UTC (`pendingCount` не больше 1000);
поиск логина — 10 в минуту на владельца и 40 в минуту на инстанс (ключи выше); не более 1000 человек с доступом к колоде; запрос можно отозвать (`:withdraw`), он освобождает один из 20 слотов. Они зафиксированы в
[`contracts/decks/access.json`](../../contracts/decks/access.json) и проверяются `AccessServiceIntegrationTest`.
Константы публикации (Share/8, #430) — контракт, а не ключи: не более 5 тегов по 1–32 символа, «Что нового» 1–500 символов,
уровень из одного закрытого списка (A1–C2, начальный, средний, продвинутый); порог каталога 10 материалов и 1 упражнение
только показывается (каталог — эпик 3); заголовки для подсказки языка и темы берутся у не более 20 материалов. Они зафиксированы
в [`contracts/decks/publication.json`](../../contracts/decks/publication.json).
Жалобы (Share/15, #437): текст до 1000 символов, срок рассмотрения 30 дней, хранение 3 года, причины — закрытый список
([`contracts/moderation`](../../contracts/moderation/README.md)); это константы, как и строка «Срок и хранение жалобы» выше.
Planner query/memory bounds и CSS tokens имеют другие причины изменения.
Повторяющийся `@Transactional(timeout=10)` не превращается в один глобальный
таймаут без измерений блокировок.

## Проверка и rollback

Неверное значение backend policy приводит к ошибке старта. Тесты должны
проверять default, края диапазона и независимость соседних областей. Если
новый предел вызывает нагрузку или ломает UX, вернуть предыдущий default для
новых операций; существующие revision/attempt IDs и format versions не менять.
Среда только локальная, rollout и восстановление серверных данных здесь не
заявлены.
