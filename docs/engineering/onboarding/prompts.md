# Промпты сессий онбординга

Как пользоваться: для каждой сессии вставить агенту **три блока подряд** — общую преамбулу,
блок моделей (Claude Code или Codex) и промпт сессии. Сессии идут по порядку S0 → S1 → S2 → S3 → S4;
если сессия не успела, следующая запускается промптом «Продолжение». Онбординг может стоять в
очереди вторым-третьим: промпты не предполагают, что база свежая, и заставляют её проверить.
Решения владельца — [questions](questions.md); статус — [progress](progress.md).

## Блок 1. Общая преамбула

```text
Ты ведущий агент проекта Mnema. Задача — часть эпика «Онбординг» (Issues и Mnema Kanban, номера в manifest.json). Работай
автономно до результата и проверок; спрашивай только при новом продуктовом/архитектурном выборе,
отсутствии доступа или расширении scope.

1. Инструкции. Прочитай AGENTS.md, backend/AGENTS.md, frontend/AGENTS.md, docs/README.md,
   docs/engineering/work-item-standard.md, затем пакет
   docs/engineering/onboarding/: README.md, questions.md (решения владельца 2026-10-14 — не переспрашивать),
   proposal.md, architecture.md, adr/, backlog.md, progress.md и тела своих эпика и задач. Для сборки и
   тестов на этой машине — /Users/yuzuru/AGENTS.md, workstation navigator и skill workstation-dev.

2. База. Пакет и эпики Сообщества 3–4 уже в main. Сделай fetch и начни от свежего origin/main
   в отдельном worktree; ветка feat/<issue>-<slug> на задачу или эпик. Не работай в чужих worktree,
   не удаляй/не сбрасывай чужие worktrees, volumes и untracked assets. Если в progress.md уже записана
   ветка реализации — продолжай в ней.

3. Проверка предыдущей работы (обязательна до своей задачи). По progress.md и последнему handoff
   (docs/engineering/evidence/onboarding/**/handoff-session-*.md) для каждой задачи со статусом
   in progress или local complete: коммит существует и входит в HEAD; отмеченные AC подтверждены
   тестами/evidence (запусти owning tests); канонические docs, контракты, стайлгайд, runtime policy index
   и scoped AGENTS обновлены; в task-файлах отмечены AC со ссылкой на evidence; нет висящих TODO без
   владельца; миграции не конфликтуют с базой. Расхождения сначала исправь («чистовая»), запиши их в
   свой handoff. Не верь handoff на слово — это отчёт, не доказательство.

4. Правила реализации. Миграции — только после inventory актуальной базы. Новые зависимости — только по
   root AGENTS (обоснование, 1–2 альтернативы, разрешение). UI: сначала элемент в /styleguide, только токены
   --mn-*, тексты — утверждённые в OB-001 (proposal «Тексты»). Без логов секретов и личных данных.
   Runtime owner один; retained mnema-local-v2 не используй как тестовый fixture; тесты — disposable
   PostgreSQL на этой машине, JDK 25, Node 24; общие lock в ~/.local/state/agent-dev.

5. Границы. Поставка — по root AGENTS.md («Task-scoped autonomy and merge boundary»): поручение
   довести задачу до конца разрешает ветку, коммиты, push, PR, CI и статусы задач на доске; merge — если
   поручение его называет; production и approval окружения — только по явному поручению. Шаблон и колоды
   не выкатываются без утверждения владельца. Production-флаги онбординга включаются только после OB-002.

6. Завершение (обязательно, даже если не всё успел). Независимое review диффа (ревьюер не автор кода),
   исправь findings. Полный gate на точном commit:
   (cd backend && ./gradlew clean quality); (cd frontend && npm ci && npm run lint && npm run test && npm run build);
   python3 scripts/verify_docs.py. Обнови: AC-галочки в task/epic файлах со ссылками на evidence; раздел
   «Уточнено реализацией» в proposal/architecture, если поведение уточнилось; progress.md (статус, commit,
   evidence, журнал сессий). Напиши docs/engineering/evidence/onboarding/<epic>/handoff-session-<N>.md:
   база и HEAD, что сделано по ID, отклонения от канона и почему, результаты gate (команда, итог,
   существенные warnings), миграции и rollback, что не проверено, статус «local complete, delivery pending»
   или что осталось, один конкретный следующий шаг. Закоммить handoff и progress последним коммитом.
   Следующая сессия должна продолжить без истории этого чата.
```

## Блок 2а. Модели — Claude Code

```text
Модели и делегирование: ты — ведущий (integrator), владеешь общими файлами, миграциями, progress.md и
handoff. Одновременно не больше двух саб-агентов. Код и механические правки — Sonnet 5.5, effort high;
research (официальные docs, API платформы, сверка канона) — Opus 5.5, effort medium; независимое review и
финальная проверка — Opus 5.5, effort high. Саб-агентам явно пиши: не запускать своих саб-агентов,
не коммитить общие файлы, вернуть дифф и результаты проверок. Передавай им пути инструкций и skills,
checkout и HEAD, версии JDK/Node, Docker endpoint, lock-ресурс и границы файлов; секреты не передавай.
Две параллельные задачи не трогают одни и те же файлы (обычно backend и frontend порознь).
```

## Блок 2б. Модели — Codex

```text
Модели и делегирование: ты — ведущий Sol 6.1 на extra high, integrator; владеешь общими файлами,
миграциями, progress.md и handoff. Одновременно не больше двух дочерних агентов, каждый на high:
реализация ограниченного набора файлов, research по официальным docs или независимое review диффа
(ревьюер — не автор кода). Дочерним агентам: не порождать своих агентов, не коммитить общие файлы,
вернуть дифф и результаты проверок. Передавай им пути инструкций, checkout и HEAD, версии JDK/Node,
Docker endpoint, lock-ресурс и границы файлов; секреты не передавай. Проверь фактически доступные
модели на хосте; если Sol 6.1 недоступен — ближайшая доступная, и запиши это в handoff.
```

## Блок 3. Промпты сессий

### S0 — подготовка: прототип, тексты, учебная и базовые колоды

```text
Сессия S0 онбординга: OB-001 (прототип и тексты), черновик OB-002 (раздел политики ПДн), план OB-202
(учебная колода «Как устроена память») и план OB-003 (10+ базовых колод) в MnemaDeckStudio.
Код продукта не меняется. Прототип — в design/prototype ветки реализации (design evidence), все экраны
из tasks/ob-001.md, включая завершение удержанием со знаком «палец удерживает» и звёзды только на
приветствии и поздравлениях. Тексты отредактируй скиллом russian-editorial-style. Для колод прочитай
/Users/yuzuru/Projects/MnemaDeckStudio/AGENTS.md и README.md, подготовь планы скиллом mnema-deck-plan;
не выполняй studio approve, не делай платных вызовов и записей через creator API — планы утверждает
владелец. Итог: прототип со скриншотами 320/768/1280, reduced motion, forced-colors; список текстов на
утверждение; черновик раздела политики с перечнем полей из architecture §3; планы колод с бюджетом.
Остановись на утверждении владельца: в handoff перечисли, что именно ему нужно посмотреть и решить.
```

### S1 — OB-E1: первый вход, опрос и тур

```text
Сессия S1: эпик OB-E1 по epics/ob-e1-first-entry-and-tour.md и tasks/ob-101…ob-105.md. Предусловие —
OB-001 утверждён (проверь progress.md; если нет — остановись и сообщи). Порядок: OB-101 (backend,
саб-агент) параллельно с OB-102 (frontend движок, саб-агент), затем OB-103, OB-104, OB-105.
Ключевое: движок на нативных <dialog>/popover/inert без @angular/cdk (ADR-ONB-001); завершение тура
удержанием 2 с — обобщить app-hold-to-delete-button, не копировать (Q03), обновить правило 4 стайлгайда;
Escape — пауза; ≤ 4 шагов на ветку; опрос переиспользует /api/learning-profile и /api/community/interests;
ветка «Найти готовую» видна при ≥ 4 доступных колодах; AttentionCoordinator не даёт турам, опросу и
промо-окну перекрываться; перепрохождение доступно всем; holdout 10–20 % через ExperimentService.
Evidence a11y обязательно (клавиатура, VoiceOver smoke, 320 px, forced-colors, reduced motion).
```

### S2 — OB-E2: «Моя первая колода»

```text
Сессия S2: эпик OB-E2 по epics/ob-e2-sample-deck.md и tasks/ob-201…ob-204.md, ADR-ONB-003.
Предусловия: OB-101/OB-102 local complete; план шаблона в MnemaDeckStudio утверждён владельцем

категория usage. Шаблон собери mnema-deck-build по утверждённому плану и установи на local stack через
API авторинга от аккаунта редакции; production-установка — не в scope.
```

### S3 — OB-E3: «Путь Mnema»

```text
Сессия S3: эпик OB-E3 по epics/ob-e3-path.md и tasks/ob-301…ob-305.md, ADR-ONB-002. 13 вех утверждены.
Вехи пишутся одним upsert в транзакции доменного действия (@Transactional MANDATORY), уведомление
PATH_MILESTONE — существующим NotificationPublisher в той же транзакции; backfill — bounded job без
уведомлений. «Первое занятие» и «Вернуться завтра» считают SCHEDULED и PRACTICE, не REPLAY. Без очков,
уровней, рейтингов. Если learning-core LC-E1/E2 уже в работе или влиты — сверь изменения
StudySessionRepository/AttemptRepository и не дублируй их writers. Измерь добавку на горячем пути занятия.
```

### S4 — OB-E4: ритм и награда

```text
Сессия S4: эпик OB-E4 по epics/ob-e4-rhythm-and-reward.md и tasks/ob-401…ob-403.md, ADR-ONB-004/005.
Ритм: SCHEDULED и PRACTICE в разные локальные дни ISO-недели, REPLAY — нет; «недель в ритме» только в
профиле; не в шапке, без отрицательных сообщений; формулировки exercise catalog/Study про streak уточни.
Награда (владелец решил делать): кампания PATH_REWARD в кабинете, персональный код через существующий
сервис промокодов, 7 дней с момента выдачи, дата окончания текстом, без таймера, один раз на verified
account, перепрохождение не выдаёт; production-флаг — только после OB-002.
```

### Продолжение незавершённой сессии

```text
Продолжи эпик <OB-E…> онбординга с места, где остановилась предыдущая сессия. Сначала выполни пункт 3
преамбулы целиком по progress.md и последнему handoff: перепроверь каждое заявленное «сделано»
(коммиты, тесты, AC, docs), исправь найденные расхождения, затем выполняй «следующий шаг» из handoff
и оставшиеся задачи эпика. Если handoff противоречит коду или канону — верь коду и канону, запиши
расхождение. Заверши по пункту 6.
```

### Финальная проверка эпика или всего онбординга

```text
Проведи независимую финальную проверку онбординга (или эпика <OB-E…>) без новой функциональности.
Для каждой задачи в progress.md со статусом local complete: найди коммиты, сверь каждый AC из task и
epic файлов с кодом и тестами, запусти owning tests и полный gate на текущем HEAD, проверь a11y-evidence,
актуальность proposal/architecture/контрактов/стайлгайда/runtime policy index/навигаторов, отсутствие
дублей кода и бесхозных TODO, что миграции применяются на чистой БД и поверх предыдущей, что флаги
выключают поведение. Мелкие расхождения исправь, крупные запиши как findings с ID задачи и шагом
воспроизведения. Обнови progress.md и напиши handoff-verification.md с вердиктом
«готово к delivery / не готово: <список>». Push/PR/merge/prod — только по отдельному поручению.
```
