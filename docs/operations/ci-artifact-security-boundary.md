# Mnema CI artifact and workflow-token security boundary

GitHub Actions artifacts are durable workflow data, not an extension of a runner's temporary
filesystem. Every upload therefore goes through
`.github/actions/safe-upload-artifact/action.yml`: the action scans the resolved files and only
then invokes the immutable `upload-artifact` release. The static contract in
`.github/artifact-policy.json` must exactly match every workflow upload, its generator,
retention and classification. A direct `actions/upload-artifact` step in a workflow fails the
repository policy test.

This follows GitHub's guidance that artifacts persist files between jobs and after workflow
completion, while workflow token permissions should be reduced with the `permissions` key:
[workflow artifacts](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflow-artifacts)
and [workflow syntax for permissions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions).

## Pre-upload enforcement

`scripts/verify_artifact_contents.py` expands only the inventoried paths under
`GITHUB_WORKSPACE` or `RUNNER_TEMP`, rejects symlinks and scans every matched file before the
upload starts. It blocks these known classes:

- `.env*`, kubeconfig paths, common private-key and credential filenames;
- the staging Secret manifest and staging/production rollback Secret snapshots;
- private-key headers, AWS access-key shapes, JWT shapes and unredacted auth/cookie headers;
- embedded kubeconfig credentials and raw Kubernetes `Secret` resources containing `data` or
  `stringData`;
- the explicit synthetic credential marker used by negative tests.

Failures print only the controlled policy ID, path and reason, never matching content. Hidden
files remain excluded by the upload action as a second boundary. Tests use synthetic markers
only and never read local `.env`, Keychain, kubeconfig, repository secrets or cluster Secret
values.

This is a known-secret boundary, not generic DLP or an entropy scanner. It cannot prove that an
arbitrary new encoding or sensitive business data is safe. New artifact types require a narrow
generator, explicit classification and new detection/test coverage where appropriate. Do not
weaken the scanner to make a new artifact pass.

## Workflow-token contract

All seven workflows declare top-level `permissions: {}`. Every job then declares an exact map:

| Permission | Jobs | Reason |
|---|---|---|
| `contents: read` | all jobs | checkout, immutable source/ref verification |
| `actions: read` | release render and deploy-gate jobs | download artifacts and inspect the exact predecessor run |
| `packages: write` | `deploy / build-and-push` only | publish the two replacement GHCR release images |
| `id-token: write` | `deploy / build-and-push` only | GitHub OIDC identity for build attestations |
| `attestations: write` | `deploy / build-and-push` only | publish provenance attestations for exact image digests |

No job receives `contents: write`, `deployments: write`, a blanket `read-all`/`write-all` token
or a secrets-context dump. The static verifier inventories every workflow and job, so a new
workflow, missing deny-by-default declaration or extra permission fails closed. It also rejects
obvious log-exposure modes in `run` blocks: shell xtrace, environment dumps, secrets-context
dumps and direct `secrets` expression interpolation. Secret expressions remain confined to
named step `env` bindings and values are never printed.

## Verification and change procedure

Run:

```bash
python3 scripts/verify_artifact_security_policy.py
python3 -m unittest scripts.tests.test_verify_artifact_security_policy -v
rg -n 'upload-artifact|permissions:' .github
```

To add an artifact, add one inventory entry and one safe action invocation with the same stable
policy ID. Add a safe fixture plus a synthetic rejection fixture when the data shape introduces
a new risk. Preserve the sanitized release diff and recovery evidence; Secret snapshot files are
runner-only rollback inputs and must never be inventoried.
